### A stale parquet froze t0, so two daily runs silently produced no vintage — and one day became permanently unevaluable (2026-08-28) [RESOLVED] [x2]
**Problem**: The 2026-08-27 commit carried `[ALARM: eval stale 3d]` while every step reported `rc=0`. `eval_log.jsonl` ended at 2026-08-24. Tracing `metadata.t0` across six daily commits showed the vintage stream, not the evaluator, was broken: 08-23 and 08-27 repeated the previous run's t0, and 08-25 jumped from `08-24T21` straight to `08-26T21`.
**Root cause**: `update_shadow.py` picks `t0 = parquet["price_eur_mwh"].dropna().index.max()` — it follows the DATA, and nothing asserted it moved. Two shapes follow. (a) **t0 repeats**: the `(timestamp_utc, eval_day)` dedup — added 2026-05-08 to stop stacked prediction sets — silently overwrites an identical vintage, so the run retrains, republishes an unchanged forecast, exits 0, and adds nothing evaluable. (b) **t0 jumps**: the skipped day never gets a prediction set at all, so it can never be evaluated. 2026-08-25 was lost this way, a third permanent hole alongside 06-08/06-10.
**Upstream chain (corrected same day against EDH's actual commit history — the first reading, "EDH published late", was wrong):** EDH's normal publish window is 16:1x–16:5x UTC, so the 4h cap is generous. It **skipped 08-23 and 08-27 entirely** (no `data_quality_report.json` commit on either date); the Augur runs waited the full 4h, timed out at 20:3x, and proceeded on stale data exactly as designed. 08-24 is the one that was ours: EDH published a **catch-up at 06:28 UTC** carrying 08-23's missed collection, `wait_for_edh.sh` tested only that the report's timestamp *date* was today, released the run instantly at 16:30 — and EDH's real 08-24 publish landed at **16:32:17, 90 seconds after Augur finished**. Not a partial publish; a gate that asked the wrong question.
**Recurrence — this exact mechanism was diagnosed on 2026-06-12 and not guarded.** That entry's root cause (2) reads: "with the parquet stale, t0 froze, new predictions deduped into the old vintage, and when the fix landed t0 jumped over 06-10 — **vintages are skippable by design and nothing alarms**." The mechanism, the two shapes, and the missing guard were all named. What shipped then was the *downstream* `[ALARM: eval stale Nd]` check — which fired correctly in August and pointed at `evaluate_shadow.py`, costing three days of diagnosis and one vintage. The alarm was built one step too late in the chain, and this session re-derived from scratch what June had already written down.
**Fix**: `classify_t0_advance()` in `ml/shadow/update_shadow.py` compares the new t0 against `state["last_t0"]` by **calendar date** (08-26T21 → 08-27T20 is 23h and perfectly healthy — how much of the delivery day EDH published moves the last realised hour around). Anything but +1 day is logged and persisted as `t0_advance_days`; `scripts/daily_update.sh` reads it and appends `[ALARM: t0 stale <date>]` / `[ALARM: t0 jumped Nd]` / `[ALARM: t0 backwards <date>]` to the commit subject. Non-fatal by design — a frozen dashboard is worse than a stale one. Gated on `SHADOW_UPDATE_RC=0`, or a failed run would re-fire the previous run's value.
**Fix 2 (the gate)**: `wait_for_edh.sh` now requires the report to be stamped at or after `MIN_PUBLISH_HOUR_UTC=12` as well as dated today — the NL day-ahead auction clears around 12:00 CET, so anything stamped before noon UTC cannot hold today's prices whatever date it carries. Replayed against 08-24 it waits the extra two minutes and releases on the 16:32:17 publish. The 4h fail-open cap is unchanged; it worked correctly on both skipped days.
**Pattern**: **A cursor derived from data, not from the clock, must be asserted to advance.** Detecting the breakage three days downstream is not the same as detecting it — the eval-stale alarm fired correctly and pointed at `evaluate_shadow.py`, which was blameless. When step B's health check is the only witness to step A's failure, it will name the wrong component. Give the step that owns the cursor its own alarm. Corollary for fail-open gates like `wait_for_edh.sh`: proceeding with stale data is right, but the *proceeding* has to leave a mark at the point of decision, not only in whatever breaks later. **Second pattern, from the correction**: a freshness check must test freshness, not a *proxy* for it. "Dated today" and "published since the event I need" diverge exactly when upstream is recovering from its own failure — which is precisely when you are relying on the gate.
**Status**: [RESOLVED] — guard + 7 tests in `tests/test_update_shadow.py::TestClassifyT0Advance`, gate condition tightened. The 08-25 vintage is unrecoverable; 08-26/08-27 self-heal as their hours realise. **Still open upstream**: EDH silently skips scheduled publishes (08-23, 08-27, and earlier 08-01/08-03/08-06 by the same commit history) — out of scope for this repo, but the skips are what the gate now has to absorb.

### A 45-minute LightGBM sweep died in its scoring pass on a wrong metrics attribute (2026-08-25) [RESOLVED]
**Problem**: `scripts/exp018_stage0_ablation.py` completed all 2104 walk-forward fits, then crashed writing the summary: `AttributeError: 'DMResult' object has no attribute 'p_value_two_sided'`. The compute was intact but nothing had been scored.
**Root cause**: The harness was written against an assumed DM API. `ml/shadow/metrics.py:diebold_mariano` takes `hac_lags=` (not `lags=`) and returns `p_value_one_sided` / `mean_diff` — it is a one-sided test by construction, so a two-sided p-value never existed. A hand-patch had fixed the call site but not the attribute read, and nothing exercised the scoring path before the long run.
**Fix**: Corrected the attribute, and split scoring out of the fitting loop behind `--reuse-predictions`, so `predictions.parquet` (written *before* the summary pass) can be re-scored in seconds instead of re-fitting. Recovered the run without recompute.
**Pattern**: **Exercise the whole path on a 3-vintage smoke run before launching a long sweep** — the expensive part passing tells you nothing about the cheap part after it. And any long compute should persist raw outputs before any aggregation step, so a scoring bug costs seconds rather than the run.
**Status**: [RESOLVED] — harness has `--reuse-predictions`; EXP-018/019 both scored from cached predictions.

### LightGBM ignores OMP_NUM_THREADS and oversubscribes under process-level fan-out (2026-08-25) [RESOLVED]
**Problem**: The first ablation smoke run (4 worker processes, 16-core box) made no progress in 2+ minutes. `ps` showed each worker accumulating ~4x its elapsed time in CPU — 8 tasks, ~64 threads fighting for 16 cores.
**Root cause**: `LGBMRegressor` defaults to `n_jobs=-1`, which sets LightGBM's `num_threads` **explicitly** — so the `OMP_NUM_THREADS=1` in the environment is ignored. Under `ProcessPoolExecutor` fan-out every worker then grabs the whole box.
**Fix**: `force_single_thread_lgbm()` in the harness patches `ml.shadow.lightgbm_quantile.LGBMRegressor` with a factory that defaults `n_jobs=1`, leaving production untouched. One fit went from stalled to 8s. First attempt used a subclass and failed — sklearn's `_get_param_names()` rejects `*args/**kwargs` constructors (`estimators should always specify their parameters in the signature of their __init__`); a plain factory function is the working shape.
**Pattern**: When fanning out an ML library across processes, force intra-op threads to 1 **in the library's own parameter**, not via env vars. To monkeypatch an sklearn-style estimator, wrap it in a factory — never subclass with varargs.
**Status**: [RESOLVED] — contained to `scripts/exp018_stage0_ablation.py`; `ml/shadow/` behaviour unchanged.

### Piping a long background run through `tail` hides all progress until it exits (2026-08-25) [RESOLVED]
**Problem**: A 45-minute sweep launched as `python -u script.py ... 2>&1 | tail -40` showed an empty output file for its entire runtime, so progress could only be inferred from `ps` CPU time.
**Root cause**: `-u` unbuffers Python, but `tail` buffers by design — it prints nothing until stdin closes. The unbuffered flag creates a false sense that output is live.
**Fix**: Redirect to a log file (`> run.log 2>&1`) and `tail` the file instead. Used for the EXP-019 sweep, where progress was visible throughout.
**Pattern**: For any long-running job, write to a file and read the file. Never pipe a background job's progress through a filter that only flushes at EOF.
**Status**: [RESOLVED]

### CI "Test retry logic" crashed — `fetch_with_retry` hard-coded UTF-8; Google serves ISO-8859-1 (2026-08-19) [RESOLVED]
**Problem**: GitHub Actions `test.yml` "Test retry logic" step failed on the 2026-08-19 daily commit: `'utf-8' codec can't decode byte 0xe1 in position 61936`. The step called `fetch_with_retry('https://www.google.com', max_retries=2)` as a connectivity canary.
**Root cause**: `decrypt_data_cached.py:fetch_with_retry` did `response.read().decode()` — hard-coded UTF-8. Google serves `charset=ISO-8859-1` (Latin-1 bytes like 0xe1 = á) to the default urllib User-Agent, so the UTF-8 decode fails. urllib also does not auto-decompress `Content-Encoding`.
**Fix** (commit `6f32dee`): `fetch_with_retry` now honors `response.headers.get_content_charset()` (fallback utf-8) and gzip-decompresses. Replaced the google.com canary with a deterministic local `ThreadingHTTPServer` test exercising success, transient-500→retry, and 404→no-retry — no external network, no encoding assumptions.
**Pattern**: A "canary" URL's response encoding is outside your control — never hard-code UTF-8 for an arbitrary host. And a "retry logic" test that only fetches one external URL wasn't testing retry at all.
**Status**: [RESOLVED] — CI green (run `32290476187`), deployed via Netlify auto-build on push.

### Dev/deploy migration (situla+sadalsuud) rebuilt the venv from loose pins → river 0.25 couldn't unpickle ARF → 5-day silent dashboard freeze (2026-07-03) [RESOLVED*]
**Problem**: After moving dev to situla with deploy on sadalsuud, the dashboard silently froze on 2026-06-28 data. `origin/main` had no daily commit for 5 days, yet the `augur-daily.timer` was healthy and firing nightly. The `augur-daily.service` was `failed` every night since 2026-06-29 (the day after a sadalsuud reboot at ~10:30). systemd's journal showed only the wrapper; the real error was in `logs/daily_update.log` (root-owned, mode 640): `AttributeError: Can't get attribute '__pyx_unpickle_VectorDict' on <module 'river.utils.vectordict'>`.
**Root cause**: A chain, not one bug. (1) The migration rebuilt sadalsuud's `.venv` from `requirements.txt`'s loose `>=` ranges (`river>=0.21`, `pandas>=2.2`, `numpy>=1.26`), so pip pulled bleeding-edge majors: river 0.25.0, pandas 3.0.4, numpy 2.5.0. (2) river 0.25's Cython `VectorDict` pickle helper is incompatible with the committed `river_model.pkl` (saved under ~0.21). (3) ARF's `ml.update` ran under `set -e` with the comment "production — must succeed" — STALE since the 2026-05-29 EXP-014 demotion that made ARF a *backup* signal. So a backup-signal unpickle failure aborted the whole script *before* the production LightGBM shadow step, commit, or push. LightGBM itself was fine under the new deps (verified: `shadow_model.pkl` loads, all shadow modules import, 195/195 tests pass).
**Fix** (commits `96dd499`, `affa443`): (a) Run ARF under `set +e` in `daily_update.sh`; failure now surfaces as `ARF FAIL rc=N` in the commit subject instead of killing production. (b) Regenerate `river_model.pkl` via `ml.training.warmup` under river 0.25 (consolidate→warmup→ml.update; ml.update confirmed load + 72h forecast + surcharge cache refresh). (c) Pin the verified-working set in `requirements.lock` (pip freeze). (d) `scripts/bootstrap_venv.sh` for reproducible identical venvs + situla parity. (e) Non-blocking pytest smoke gate as a pre-flight in `daily_update.sh`.
**Pattern**: (1) **Loose `>=` pins + a fresh venv = an unannounced major-version upgrade.** Any pipeline that loads pickled models across a rebuild must pin exact versions (lockfile), because cross-version pickle compat is not guaranteed — Cython-backed classes (river VectorDict) especially. (2) **A demoted/backup component must not be able to abort the promoted/production path.** When a model is demoted, audit every `set -e`/"must succeed" site that still treats it as critical — the comment lied for 5 weeks before it cost us. (3) **Silent for 5 days** because the only alive-signal is "someone notices missing commits on origin/main" — active failure alerting (systemd `OnFailure=`) is still the biggest open gap (deferred by user 2026-07-03).
**Residual risks**: (1) yanked `pandas==3.0.4` — **RESOLVED same day** (`0574e3d`): repinned to mature `pandas==2.3.3` (river/numpy/lightgbm unchanged so the pickle stayed valid, no regen); requirements.txt gained ceilings (`pandas<3`, `numpy<3`, `sklearn<2`, `lightgbm<5`) and `river==0.25.0` to stop unbounded `>=` jumping majors again; 195 tests pass on both boxes. (2) dev/prod Python skew (situla 3.14 vs sadalsuud 3.12, situla has no 3.12) — still open, but low-severity: pandas 2.3.3 ships cp314 wheels so the lock reproduces on both interpreters and both are green. (3) No active failure alert (systemd `OnFailure=`) — still open, user-deferred; remains the biggest gap since the outage was silent for 5 days.
**Status**: [RESOLVED for the outage] — production restored, decoupled, reproducible, repinned off the yanked pandas, smoke-gated. Open follow-ups: `OnFailure=` alerting; optional py3.12 on situla for true interpreter parity; numpy-2.5 `pd.Timedelta` bare-int DeprecationWarnings in `ml/shadow/update_shadow.py` (lines ~207/271 — will error on a future numpy, harmless while numpy is pinned).

### "ARF OK | eval rc=0" while ARF published empty forecasts and eval vintages silently vanished (2026-06-12) [RESOLVED]
**Problem**: Investigating two missing eval-log rows (2026-06-08, 2026-06-10) revealed the EDH v2.2 break's blast radius was bigger than the 2026-06-10 entry recorded: (a) ARF's archives for 06-08 (both runs) and 06-09 contain ZERO forecast hours — the live `augur_forecast.json` was empty those days while three daily commits said "ARF OK"; (b) eval vintages 06-08 and 06-10 have zero rows in `calibration_history` — permanently unevaluable; (c) the 06-09 eval row has `arf_mae: null` because `find_arf_archive_for_day` picked the empty 06-08 archive with no fallback to an earlier non-empty one.
**Root cause**: Three independent mechanisms, all downstream of the v2.2 parser break. (1) `daily_update.sh`'s status line reflects exit codes only — `ml.update` exits 0 even when `generate_forecast` emits zero hours (every hour skipped because `fb.build` found no load data). (2) `eval_day` in `shadow_state.json` is a forecast *vintage* keyed to the date of the last realised parquet price (t0); with the parquet stale, t0 froze, new predictions deduped into the old vintage, and when the fix landed t0 jumped over 06-10 — vintages are skippable by design and nothing alarms. (3) The archive-lookup in `evaluate_shadow.py` takes the single most recent file before the eval day, empty or not.
**Fix**: Two non-blocking post-run guards in `daily_update.sh` (commit `1c33daa`), surfacing in the commit subject like the pre-flight alarms: `[ALARM: ARF forecast Nh]` when the published forecast spans <24h, `[ALARM: eval stale Nd]` when no eval row lands for >2 days. Incident documented on augur#14 (the umbrella for gap detection); the eval-vintage gaps themselves are unrecoverable.
**Pattern**: Third recurrence of the silent-failure factory → promoted to the table above as "rc=0 is not output quality". Plus one research-method corollary: `eval_log.jsonl` rows are NOT comparable at face value — `n_overlap_hours` varies 24/48/72 depending on *when* a vintage was logged (prompt vs catch-up), so per-day coverage/MAE baselines must be computed from `calibration_history`, not the eval log (this redirected the EXP-015 baseline).
**Followup (corrected same day)**: The 48h truncation (filed as **augur#26**) was first blamed on the v2.2 file-window narrowing — wrong. Chasing the "5 hours with exchange lags" anomaly disproved it: `fb.build()` doesn't skip on missing load; it skips on missing 1h/24h **price lags**. Real cause: `OnlineFeatureBuilder.price_history` deque(maxlen=200) was sized for hourly data ("~8 days"); v2.2's 15-min resolution shrank it to ~50h (verified: 200 entries, all 15-min spacing, span 49.8h) and generate_forecast's ~100 future quarter-point pushes evicted history to ~24h → `lag_24h` failed for the first ~21 forecast hours. Fixed `f49a1c8` (maxlen 800); recovery check on the 06-13/06-14 runs' `Generated NN-hour` line. **Meta-lesson: when an upstream changes data *resolution*, audit every count-based buffer/window sized in "entries" that assumed the old cadence** (deque maxlen, `_get_recent_prices` windows, rolling-stat min-coverage thresholds). The window narrowing itself is real but secondary (long-horizon exogenous quality) — filed EDH-side as energydatahub#33; elspot follow-ups from 2026-06-07 finally filed as energydatahub#34.
**Status**: [RESOLVED] — guards shipped, root cause fixed; augur#26 stays open pending the ≥72h recovery confirmation.

### EDH v2.2 envelope wrap ALSO broke Augur Python parsers (recurrence of 2026-06-07, 3 days later) (2026-06-10) [RESOLVED]

Three days of silent parquet-stalling followed. **Followup**: Augur#? not filed (no separate ticket; resolved in this session). Permanent eval-log gap: 2026-06-08 has no LGBM prediction set targeting it (no successful shadow update ran during the outage), so no eval row can be reconstructed for that day. Filed as follow-up.

**Problem**: First manual dry-run of EXP-009 M3 shadow pipeline on sadalsuud crashed with `ModuleNotFoundError: No module named 'lightgbm'`. The M3 commits added `lightgbm>=4.0` to `requirements.txt` but cron doesn't `pip install -r requirements.txt` — it just activates the venv and runs.
**Root cause**: `scripts/daily_update.sh` activates `.venv` and runs Python directly. There's no dependency-install step. New deps land in requirements.txt locally, get pushed to origin, sadalsuud pulls main, and the cron uses whatever the venv currently has — which may not match requirements.txt.
**Fix**: `pip install lightgbm>=4.0` manually in sadalsuud's venv. Updated `memory/sadalsuud-server.md` (auto-memory) with the manual-install discipline.
**Pattern**: When adding a new Python dep that ships in cron, install it manually on sadalsuud BEFORE the next cron, OR extend `daily_update.sh` with an idempotent install (`pip install -r requirements.txt --quiet` is fast on a no-op). The dry-run-before-cron discipline catches this in 30 seconds; the alternative is silent shadow-block failure for a day until someone reads the log.
**Status**: [RESOLVED] — installed manually 2026-04-30; augur#12 (systemd migration) should also address this with a service-file `ExecStartPre` that ensures deps are current.

### Path-fix commit left orphan tracked files in the wrong location (2026-04-30) [RESOLVED]
**Problem**: M3 review fixup A redirected ARF forecast archives from `static/ml/forecasts/` (where the buggy `output_dir.parent` calculation wrote them) to `ml/forecasts/` (the documented location). On sadalsuud, the migration `mv` for the existing files surfaced as a working-tree disaster: `git status` showed dozens of deleted files, and the deletions weren't committed to ANY branch. The next `git pull` or branch checkout would have either conflicted or wiped the moved files.
**Root cause**: `static/ml/forecasts/` was NOT gitignored (only `static/data/*.json` was). So the buggy code had been committing forecast archives to git for weeks. The path-fix commit corrected future writes but didn't address the historical files at the old path — leaving them tracked forever, and any filesystem-level migration showing up as untracked deletions on every machine that runs the cron.
**Fix**: On sadalsuud, `git restore static/ml/forecasts/` to undo the local deletion (files are tracked, restoration is a checkout); leave the old files in place as frozen historical archives; new writes go to the new path. Both locations now exist; the duplication wastes ~few MB.
**Pattern**: A path-fix commit should EITHER (a) include `git rm -r <old-path>/` in the same commit so the move is atomic, OR (b) add `<old-path>/` to `.gitignore` so future writes to that path stop being tracked but historical files remain. Option (a) loses history, option (b) leaves orphan tracked files. Check whether the old path was gitignored BEFORE the fix; if not, the fix is incomplete without one of those follow-ups.
**Status**: [RESOLVED] — sadalsuud and Windows both reconciled; old archives retained as historical reference.

### Pandas mixed timezone offsets in CSV parse to object dtype (2026-04-28) [RESOLVED]
**Problem**: `pd.read_csv("metrics_trajectory.csv", parse_dates=["commit_date"])` returned the column as object dtype instead of datetime64. Subsequent `.dt.tz_convert(...)` raised `AttributeError: Can only use .dt accessor with datetimelike values`.
**Root cause**: The CSV had ISO-8601 timestamps spanning the EU DST transition — values like `2026-03-26T15:18:55+01:00` and `2026-03-29T16:45:06+02:00` in the same column. Pandas' `parse_dates` heuristic falls back to object dtype rather than picking a single dtype with mixed offsets.
**Fix**: Don't rely on `parse_dates=`. Read first, then explicitly `pd.to_datetime(col, utc=True)` — `utc=True` normalises offsets to UTC, producing a clean tz-aware datetime64 column. Pattern saved in `_load_trajectory()` in `scripts/build_arf_retrospective_figures.py`.
**Pattern**: Any time-series CSV that spans a DST boundary (or aggregates from multiple timezone sources) will trigger this. Default to `pd.to_datetime(..., utc=True)` for any timestamp column you intend to use as a real datetime. The `parse_dates=` shortcut only works for single-offset data.
**Status**: [RESOLVED]

### Python stdout encoding breaks on Unicode arrows under Git Bash (2026-04-19, recurred 2026-04-29) [RESOLVED]
**Problem**: Probe script printing `→` arrow crashed with `UnicodeEncodeError: 'charmap' codec can't encode character '\u2192'` on Windows. Aborted a multi-probe parallel run mid-way.
**Root cause**: Windows Python defaults to cp1252 stdout when invoked via Git Bash without explicit encoding. Non-ASCII output fails immediately.
**Fix**: Set `PYTHONIOENCODING=utf-8` before the python invocation, or avoid non-ASCII characters in print statements for committed scripts.
**Recurrence (2026-04-29)**: Same trap in `ml/shadow/backtest.py` startup line — `print(f"... {a} -> {b} ...")` originally written with a Unicode arrow. Caught immediately on first invocation; one-character fix.
**Pattern**: If running ad-hoc python on Windows Git Bash with any non-ASCII output, prepend `PYTHONIOENCODING=utf-8`. For committed scripts use ASCII-only separators (`->`, `..`) over Unicode — environment-independent and survives cp1252 callers. Two recurrences in 10 days makes this a write-time discipline, not a runtime workaround.
**Status**: [RESOLVED]
