| Symptom | Likely cause | Fix |
|---------|-------------|-----|

See `memory/gotcha-log.md` 2026-06-10 entry. |
| Daily commit subject shows `[ALARM: dep probe failed — shadow skipped]` | venv on sadalsuud has corrupted/missing lightgbm/river/pandas | `ssh sadalsuud && cd ~/local_dev/augur && .venv/bin/pip install --force-reinstall lightgbm river pandas` then verify with the dep-probe one-liner from `scripts/daily_update.sh` |
| Daily commit subject shows `[ALARM: t0 stale <date>]` | The parquet did not advance since the previous run — EDH published nothing usable, so `wait_for_edh.sh` reached its **03:00 UTC deadline** and proceeded on yesterday's data (the gate is fail-open by design). ⚠️ **Until augur#31 closed on 2026-09-11 the gate's size expectation had decayed to 96**, so a run in that window may instead have *accepted* a pre-auction publish carrying same-day prices only. If `t0` advanced but the first 24 forecast hours look wrong, suspect that rather than a stall. The run overwrote yesterday's vintage and produced nothing evaluable. | Nothing to fix in Augur — the gate and guard both behaved correctly. **Since 2026-09-10 the gate checks this itself** — `wait_for_edh.sh` polls EDH's open `publish-failure` issues (unauthenticated `api.github.com`, python3 stdlib; `gh` is *not* installed on sadalsuud) and gives up early with `[ALARM: EDH publish FAILED upstream — repo#N]` when one was opened **after that run started**. If you see that marker, the diagnosis below is already done and the issue number is in the subject. It fires only on the **first** night of a failure streak — EDH opens one issue per streak — so on later nights you still get the plain gate-timeout marker and the manual check below applies. **Check EDH's own alarm first, it is faster and more specific:** `gh issue list --repo ducroq/energydatahub --search "Daily publish is failing" --state open`. An open issue names the failing run and how long it has been going; it self-closes on recovery. If there is **no** issue, that is worse news, not better — EDH's alert job lives inside `collect-data.yml` and cannot fire for a run that never started (dropped cron, queue outage, disabled workflow), so no issue plus a stale `t0` means the pipeline may not be running at all. Then check publishes directly: `gh api "repos/ducroq/energyDataHub/commits?path=data/data_quality_report.json&per_page=5" --jq '.[].commit.committer.date'` — and note only `Update energy data` commits carry data; `Record shape observation` commits land even on failed runs, so a live-looking history can publish nothing (2026-08-31..09-04, five vintages lost). Repeated misses are an EDH workflow problem (ducroq/energyDataHub#50, #51). |
| Daily commit subject shows `[NOTE: sub-naive L/N]` | LightGBM scored below the seasonal-naive floor on L of the last N scored eval days (N is 7 once enough scored rows exist). **A result, not a fault** — deliberately `NOTE:` and not `ALARM:`, so it does not enter the heartbeat's soft-failure path. Nothing failed and no data was lost. | Do **not** treat as an incident and do not change the model on it. The verdict landed 2026-11-06, confirmed (`docs/archive/hypothesis-log-resolved.md` [2026-09-06]); it read the *mean*, not a streak, so this marker is now background. Note the window is the last 7 rows **carrying a usable naive score**, not 7 calendar days — after an EDH outage it can span weeks, and since 2026-09-11 the scan really does walk back that far (it was capped at the last 10 rows, which with enough excluded rows could stop the marker firing at all). Context and the regime caveat: augur#29. Progress toward the verdict is printed every run as `Seasonal-naive verdict trigger: N/21 qualifying rows` — read that rather than counting the log by eye, where a 1-hour row is indistinguishable from a 24-hour one. |
| Daily commit subject shows `[ALARM: EDH entsoe short N/M accepted after 4h]` | The **primary** feed published short and no fuller publish arrived within the hold window, so the gate accepted it rather than burning to the 03:00 deadline. The vintage is **degraded, not lost**: t0 may anchor on data without day-ahead prices. | Expect a `[ALARM: t0 held back …]` or `[ALARM: t0 stale …]` on the same subject — that is the consequence, and it is the measured one. Root cause is upstream short-delivery (EDH #74: a four-day query answered with one day, silently). Nothing to fix in Augur. If this becomes frequent, `EDH_SHORT_HOLD_HOURS` tunes the wait; `0` accepts immediately. |
| Daily commit subject shows `[NOTE: EDH <feed> short at publish N/M]` | The EDH publish carried fewer points than the 75th-percentile expectation for a **secondary** feed (`load_forecast`). The gate is designed to proceed through this — 2026-08-26's only publish was short, and refusing it would have cost the vintage outright. **Not a fault**, and demoted from `ALARM:` to `NOTE:` on 2026-09-11 for exactly that reason: as an ALARM it made the 06:00 heartbeat mail "pipeline FAILED" for the healthy 2026-09-10 run (`shadow rc=0/eval rc=0`, `t0_held_back_hours=0.0`, full 72h forecast pushed). | Nothing to do. The gate sees a point count, not a feature row, so it cannot know whether the short feed costs anything — `latest_feasible_t0` decides that, and when it does cost something the answer arrives on the same subject as **`[ALARM: t0 held back Nh — <feeds> short]`**. That marker is the fault; this one is the early warning beside it. If the short feed persists for days the derived expectation absorbs it and the NOTE stops (same decay mechanism as augur#31). |
| Daily run prints `NOTE: N recent eval row(s) scored on <12 paired hours` | An eval row was scored against the seasonal-naive floor on too few paired hours to weigh, and was excluded from both the 7-row window and the ≥21 verdict trigger. Happens after vintage damage: the baseline pairs only hours whose source day exists in the parquet. The 2026-09-09 row paired **one** hour, at horizon 25, and scored +0.762. | Nothing to fix — the row is still written and still readable, it just is not counted. If these are frequent, the cause is upstream vintage loss (t0 alarms, EDH outages), not the evaluator. Floor is `MIN_NAIVE_HOURS` in `scripts/daily_update.sh`, default 12. |
| Daily commit subject shows `[NOTE: naive thin N]` | N of the last 10 eval rows were scored against the seasonal-naive floor on fewer than 12 paired hours and excluded from the count. **Not a fault** — the evaluator worked; there was too little overlap to weigh. Sustained thin rows mean the augur#29 verdict trigger has stopped advancing. | Look upstream, not at the evaluator: thin rows come from vintage damage (t0 alarms, EDH outages) leaving no source day to pair against. Check the `Seasonal-naive verdict trigger: N/21` line in `logs/daily_update.log` to see where the count actually stands. |
| Daily commit subject shows `[ALARM: naive unscored N]` | Eval rows are landing but carry no `lightgbm_skill_vs_naive`, so the floor is no longer being computed. **This one is a real fault** — the instrument broke, not the model. | Check `ml/data/training_history.parquet` exists and is readable, has a `price_eur_mwh` column and no duplicate timestamps, and that recent `calibration_history` rows carry `t0_utc`. `evaluate_shadow.py:load_price_history` logs which of these it hit. Rows written before 2026-09-06 have no naive fields and are not counted here. |
| Daily commit subject shows `[ALARM: t0 jumped Nd]` | The parquet caught up by more than a day. **Two causes, and they need different responses.** (a) *Upstream* — the run after an EDH skip; check `memory/upstream-edh.md` and EDH's `publish-failure` issues. (b) *Ours* — the gate was consuming an older unconsumed publish and something delayed one run past the same-day publish, which then superseded it (2026-09-13: `t0` 09-12 → 09-14 with EDH publishing normally on both days). **Check (b) first**: `ssh sadalsuud 'bash -s' < scripts/check_gate_lag.sh`. If it says LAGGED, the skip was ours. The skipped day never got a prediction set and is **permanently unevaluable** — it will be a hole in `eval_log.jsonl` forever. | No recovery possible for the lost day. Note it wherever a trailing-window metric reads `eval_log.jsonl` (e.g. EXP-018a Stage 2) so the hole isn't read as a zero. Known holes: 2026-06-08, 2026-06-10, 2026-08-25. |
| Daily run finishes ~16:35 UTC every night, all markers clean, but the forecast is anchored a day back | **The gate is consuming yesterday's publish.** Readiness is *strictly newer than the last consumed report* — it has no test for the report being from today. The unit fires 16:30 UTC and EDH publishes ~18:00–18:56 UTC, so **any EDH day with more than one publish** leaves one unconsumed and every later run then finds it waiting and releases on it in seconds. The lag never self-corrects, and **every guard reads green**, because `t0` still advances exactly +1 day per run. Seeded twice in seven days (2026-09-04, four publishes; 2026-09-10, two) for five lagged nights before anything noticed. | Ask directly: `ssh sadalsuud 'bash -s' < scripts/check_gate_lag.sh` prints `gate is CURRENT` or `gate is LAGGED by Nd` and exits non-zero on the latter. Longhand: `grep 'READY:' logs/daily_update.log \| tail -5` and compare each consumed report's date with the run's. A lagging run also shows `t0 = <run date> 21:00Z` in `ml/models/shadow/shadow_state.json`, where a current one shows `<run date +1> 21:00Z`. ⚠️ **Should no longer be reachable since 2026-09-14**: the gate's clause (c) holds a publish that was already sitting there when the run started. If you see this shape anyway, clause (c) is disabled or broken — check `EDH_STALE_GRACE_HOURS` is not set to something huge, and that the gate on the box is the committed version (`ExecStartPre` runs BEFORE `daily_update.sh` pulls, so a gate change is one run late unless pulled by hand). augur#34; `docs/hypothesis-log.md` [2026-09-14]. |
| Daily commit subject shows `[ALARM: EDH publish Nh stale accepted after Nh]` | Clause (c), working (augur#34, 2026-09-14). The newest EDH report was already there when the run started, the gate held `EDH_STALE_HOLD_HOURS` for a fresher one, none came, and it proceeded rather than failing closed. **The vintage is anchored on data up to a day old** — that is the cost, and it is named rather than silent. | Usually upstream published nothing tonight; check `memory/upstream-edh.md` and EDH's `publish-failure` issues. Nothing to fix in Augur. Expect a `[ALARM: t0 stale …]` on the same subject — that is the same fact one layer down. If it fires on a night EDH *did* publish normally, clause (c) is mis-tuned: `EDH_STALE_GRACE_HOURS` (default 2h) may be too tight for a publish that lands just before 16:30 UTC. |
| Daily commit subject shows `[ALARM: eval stale Nd]` | No new row appended to `eval_log.jsonl` for >2 days. Usually **downstream** of a t0 alarm rather than an evaluator fault — a day needs ≥24 realised hours in `calibration_history` before it is eligible. | Check `t0_advance_days` in `ml/models/shadow/shadow_state.json` first, and count realised hours per `eval_day`. If a recent day sits just under 24, it self-heals on the next run. See `memory/gotcha-log.md` 2026-08-28. |
| Daily run finishes late, up to the 03:00 UTC deadline, instead of ~16:35 | `wait_for_edh.sh` polled without its **content contract** being satisfied (rewritten 2026-09-01, `7d0066d`): the EDH report must be strictly newer than the last consumed *and* `entsoe` must carry ≥ the **75th-percentile** point count of recent publishes (the median until augur#31, 2026-09-11). So either EDH published nothing, or it published something short — a pre-auction collection holds same-day prices only (96 vs 192), since the NL day-ahead auction clears ~12:00 CET. **This is the gate working, not a hang.** | Expected fail-open behaviour — it proceeds on stale data rather than freezing the dashboard, and the `[ALARM: t0 stale …]` marker on the same commit records the consequence. `logs/.edh_gate_state` holds the last consumed report timestamp; `logs/daily_update.log` carries the per-poll reason (`entsoe only N points (want >= M)`). A correctly refused short vintage looks identical to a hang from the outside — confirm against the log before intervening. There is **no** `MIN_PUBLISH_HOUR_UTC` floor any more; the old 4h cap and noon-UTC test were removed because GitHub defers EDH's cron unpredictably (observed 00:18–21:14 UTC) and a clock floor shut the gate on good publishes. |
| Daily commit subject shows `[ALARM: profile forecast failed rc=N]`, `[ALARM: profile forecast Nh of 72]` or `[ALARM: profile forecast t0 behind shadow]` | The dashboard's forecaster (`ml/shadow/update_profile.py`, ADR-009) failed, or wrote fewer than 72 hours. On failure the dashboard keeps the previous night's `augur_forecast_profile.json`. `no last_t0` means `update_shadow` never ran. `t0 behind shadow` means the step never ran, or wrote for an older `t0`, after a good shadow run: check the log for `Running profile forecast`. A short forecast means price holes: the rule needs 5 matching days with prices within 56 days of each hour | Read `logs/daily_update.log`. Rerun by hand with `python -m ml.shadow.update_profile` on sadalsuud and push. To fall back to LightGBM, point `dashboard.js:loadAugurForecast` at `augur_forecast_shadow.json` |
| Daily commit subject shows `[ALARM: FM shadow failed exit N]` | The Chronos-Bolt shadow (`ml/shadow/update_fm.py`, EXP-021a Stage 3) failed. Production's forecast is already written: the step runs last in the shadow block, under `timeout -k 30 900`, and the commit normally still lands. `exit 124` is the timeout. The exception is a kernel OOM kill: the unit has `OOMPolicy=stop`, so systemd would stop the job before the commit (peak was 1.4 GB in the rehearsal, on a 30 GB host). A `ModuleNotFoundError` for torch or chronos means the venv was not rebuilt from `requirements.lock`; a Hugging Face error means the pinned revision is missing from `~/.cache/huggingface/hub`, because the step runs with `HF_HUB_OFFLINE=1` | Read `logs/daily_update.log`. Each missed night is a vintage the 14-vintage read loses, and it cannot be reconstructed, so fix it the same day. To stop the shadow, remove the step from `scripts/daily_update.sh` |
| Daily commit subject shows `[ALARM: FM regret failed exit N]` | The regret pass over `ml/models/shadow/fm_state.json` failed after a good FM run. Nothing is lost yet: the next successful pass scores whatever is pending, as long as it stays inside the 30-day history | Read `logs/daily_update.log`, then rerun `python -m ml.shadow.regret --state ml/models/shadow/fm_state.json --regret-log ml/shadow/fm_regret_log.jsonl --model-arm fm` |
| Build fails with decryption error | Missing or wrong encryption keys | Check Netlify env vars match energyDataHub keys |
| Chart renders but no live data | Energy Zero API down or CORS issue | Check browser console; API tries yesterday if today fails |
| ML inference outputs empty forecast | Model not trained yet | Train with `python -m ml.training.warmup` first (ARF) or wait for next nightly shadow update (LGBM regenerates from parquet) |
| Timezone appears wrong in winter | Hardcoded +2h offset somewhere | Use `Intl.DateTimeFormat` with `timeZone: 'Europe/Amsterdam'` |
