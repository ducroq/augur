# Runbook

## Principles

- **Forecast accuracy > dashboard polish** — the ML pipeline is the core value; the dashboard is the delivery mechanism
- **Continuous learning > batch perfection** — ship a working model, improve daily with online learning
- **Temporal splits only** — never random train/test splits on time series; always split by date
- **energyDataHub is upstream, not ours** — don't modify its data formats; adapt to them

## Local Development

### Prerequisites

- Python 3.12 (deploy box sadalsuud pins 3.12; the venv is locked in `requirements.lock`). Dev box situla currently runs 3.14 — same pinned package set, cp314 wheels resolve, but for exact parity install 3.12.
- [Hugo](https://gohugo.io/) v0.124.0+
- Node.js 16+ (for npm scripts)
- Encryption keys from energyDataHub (ENCRYPTION_KEY_B64, HMAC_KEY_B64)

### Setup

```bash
git clone https://github.com/ducroq/augur.git
cd augur
npm install

# Reproducible Python venv from the pinned lockfile (creates ./.venv).
# Installs the EXACT versions in requirements.lock — NOT the loose ranges
# in requirements.txt (a fresh `pip install -r requirements.txt` is what
# silently pulled bleeding-edge majors during the 2026-07-03 migration and
# broke the ARF pickle). --dev also installs pytest for the test suite.
scripts/bootstrap_venv.sh --dev
source .venv/bin/activate
```

### Running

```bash
# Set keys (bash) — or place them in a .env file (the daily job sources it)
export ENCRYPTION_KEY_B64="your_key"
export HMAC_KEY_B64="your_key"

# Decrypt data
python decrypt_data_cached.py --force

# Run tests
python -m pytest tests/ -q

# Dashboard
hugo server -D
```

## Deployment

### Build Pipeline (Netlify)

The `netlify.toml` build command runs `scripts/netlify_build.sh`:
1. `pip install cryptography` — Python deps
2. `python decrypt_data_cached.py --force` — fetch + decrypt from energyDataHub
3. `hugo --minify` — build static site

Forecasts are generated by the daily systemd timer on sadalsuud (`scripts/daily_update.sh`, gated by `scripts/wait_for_edh.sh`), not during the Netlify build.

### Pre-deploy checklist

- [ ] Encryption keys set in Netlify environment variables
- [ ] energyDataHub publishing to GitHub Pages
- [ ] `--force` flag present in build command (critical — see ADR-003)
- [ ] ML model artifact exists in `ml/models/` if inference step enabled

### Post-deploy verification

- Dashboard loads at deployed URL
- Chart renders with current day's data
- Energy Zero live data refreshes (check browser console)
- Forecast data timestamp is recent (< 24 hours)

### Webhook Flow

1. energyDataHub GitHub Action runs daily at 16:00 UTC
2. Collects, encrypts, publishes to GitHub Pages
3. Triggers Netlify rebuild via `NETLIFY_BUILD_HOOK` secret
4. Netlify decrypts fresh data, runs inference, builds, deploys

## Adding a New Data Feature (ML)

1. Identify the data source in energyDataHub's published JSON files
2. Add extraction logic in `ml/features/online_features.py`
3. Ensure timestamp alignment with existing features (hourly resolution)
4. Handle unit conversion if needed (see `memory/data-formats.md`)
5. Retrain model and evaluate impact on forecast accuracy
6. Update `memory/data-formats.md` if the source has quirks

## Adding a New Data Source to Dashboard

1. Add collector in energyDataHub (separate repo)
2. Update `ml/features/online_features.py` to use the new source as features
3. If client-side visualization needed, update `static/js/modules/data-processor.js`
4. Add to constants in `static/js/modules/constants.js`

## Monitoring the daily job

Three layers, added 2026-08-30/31. Each covers a case the others structurally cannot, so they are deployed together or not at all. Unit files in `scripts/systemd/`; install and rollback recipes in its README.

| Layer | Fires when | Cannot see |
|---|---|---|
| `OnFailure=augur-alert@` (drop-in `augur-daily.service.d/alert.conf`) | the unit **dies** — `set -e` abort, timeout, ExecStartPre failure | anything that exits 0 |
| `augur-heartbeat.timer`, 06:00 UTC | no `Daily update` commit in >30h, timer not enabled+active, or unpushed commits | a bad run that still commits |
| the same heartbeat, reading the commit **subject** | soft failures: `[ALARM: ...]`, `ARF FAIL`, any non-zero step `rc=N`, `rc=skip` | a failure the script never names |

**Why three.** `daily_update.sh` ends with `git diff --cached --quiet && echo "No changes to commit" || {commit; push;}`, so a run producing nothing exits 0 and the unit *succeeds* — `OnFailure=` cannot fire for it. And on 2026-08-30 the production model crashed while the run completed and committed: `shadow rc=1` in the subject, unit green, heartbeat green. Every soft-failure alarm this pipeline raises rides in the commit subject by design, so the third layer is what gives them a reader.

**Channel.** `scripts/notify_email.py`, stdlib only, reading `[email_credentials]` from FluxusSource's gitignored `secrets.ini` on sadalsuud — the same sender `nexusmind-alert@.service` uses. Deliberately no new notification service. Missing creds degrade to a line in `logs/alerts.log` and still exit 0: an alerter that throws inside systemd's failure handling only adds noise. `AUGUR_NOTIFY_SECRETS` overrides the path so a dev-box dry-run cannot send a real email.

**Accepted blind spot.** The heartbeat runs *on* sadalsuud, so it cannot report that sadalsuud is down. Closing that needs an off-host dead-man's switch, i.e. a new service — declined 2026-07-17. The residual case is also the one where daily commits visibly stop.

**Checking it by hand**

```bash
ssh sadalsuud "systemctl show augur-daily.service -p OnFailure --value"   # augur-alert@augur-daily.service.service
ssh sadalsuud "systemctl list-timers augur-heartbeat.timer"
ssh sadalsuud "sudo systemctl start augur-heartbeat.service && tail -3 ~/local_dev/augur/logs/alerts.log"
ssh sadalsuud "sudo systemctl start augur-alert@augur-daily.service"      # end-to-end: sends ONE real email
```

`alert_failure.sh` holds a 3h burst guard, armed only after a **confirmed** send — a skipped or failed email must not silence the next real alert. So a second test fire within 3h logs `email skipped (burst guard)` rather than sending; that is correct, not a fault.

**Reading an alert.** The email leads with 40 lines of `logs/daily_update.log`, because that is where the error text is: `augur-daily.service` sets `StandardOutput/StandardError=append:`, which **overrides** systemd's journal capture, so `journalctl -u augur-daily.service` holds only lifecycle lines — start, exit code, timeout — and never script output.

## Common Problems

| Symptom | Likely cause | Fix |
|---------|-------------|-----|
| Dashboard shows old data | energyDataHub Action didn't run or webhook didn't trigger | Check Action logs, verify NETLIFY_BUILD_HOOK secret |
| Dashboard 72h forecast shows only a short stub | EDH schema bumped → Augur parsers reading stale shape; `WARNING ENTSO-E data missing` lines in `logs/daily_update.log` despite EDH being healthy | Audit `ml/data/consolidate.py` parsers + `static/js/modules/data-processor.js` + `tab-charts.js` for direct top-level `data['<source>']` access; add a `data.get('data', data)` shim. See `memory/gotcha-log.md` 2026-06-10 entry. |
| Daily commit subject shows `[ALARM: dep probe failed — shadow skipped]` | venv on sadalsuud has corrupted/missing lightgbm/river/pandas | `ssh sadalsuud && cd ~/local_dev/augur && .venv/bin/pip install --force-reinstall lightgbm river pandas` then verify with the dep-probe one-liner from `scripts/daily_update.sh` |
| Daily commit subject shows `[ALARM: t0 stale <date>]` | The parquet did not advance since the previous run — EDH published nothing usable, so `wait_for_edh.sh` reached its **03:00 UTC deadline** and proceeded on yesterday's data (the gate is fail-open by design). The run overwrote yesterday's vintage and produced nothing evaluable. | Nothing to fix in Augur — the gate and guard both behaved correctly. **Check EDH's own alarm first, it is faster and more specific:** `gh issue list --repo ducroq/energydatahub --search "Daily publish is failing" --state open`. An open issue names the failing run and how long it has been going; it self-closes on recovery. If there is **no** issue, that is worse news, not better — EDH's alert job lives inside `collect-data.yml` and cannot fire for a run that never started (dropped cron, queue outage, disabled workflow), so no issue plus a stale `t0` means the pipeline may not be running at all. Then check publishes directly: `gh api "repos/ducroq/energyDataHub/commits?path=data/data_quality_report.json&per_page=5" --jq '.[].commit.committer.date'` — and note only `Update energy data` commits carry data; `Record shape observation` commits land even on failed runs, so a live-looking history can publish nothing (2026-08-31..09-04, five vintages lost). Repeated misses are an EDH workflow problem (ducroq/energyDataHub#50, #51). |
| Daily commit subject shows `[NOTE: sub-naive L/N]` | LightGBM scored below the seasonal-naive floor on L of the last N scored eval days (N is 7 once enough scored rows exist). **A result, not a fault** — deliberately `NOTE:` and not `ALARM:`, so it does not enter the heartbeat's soft-failure path. Nothing failed and no data was lost. | Do **not** treat as an incident and do not change the model on it. The verdict is pre-committed in `docs/hypothesis-log.md` [2026-09-06] on ≥21 scored rows and reads the *mean*, not a streak. Note the window is the last 7 rows **carrying a naive score**, not 7 calendar days — after an EDH outage it can span weeks. Context and the regime caveat: augur#29. |
| Daily commit subject shows `[ALARM: naive unscored N]` | Eval rows are landing but carry no `lightgbm_skill_vs_naive`, so the floor is no longer being computed. **This one is a real fault** — the instrument broke, not the model. | Check `ml/data/training_history.parquet` exists and is readable, has a `price_eur_mwh` column and no duplicate timestamps, and that recent `calibration_history` rows carry `t0_utc`. `evaluate_shadow.py:load_price_history` logs which of these it hit. Rows written before 2026-09-06 have no naive fields and are not counted here. |
| Daily commit subject shows `[ALARM: t0 jumped Nd]` | The parquet caught up by more than a day, usually the run after an EDH skip. The skipped day never got a prediction set and is **permanently unevaluable** — it will be a hole in `eval_log.jsonl` forever. | No recovery possible for the lost day. Note it wherever a trailing-window metric reads `eval_log.jsonl` (e.g. EXP-018a Stage 2) so the hole isn't read as a zero. Known holes: 2026-06-08, 2026-06-10, 2026-08-25. |
| Daily commit subject shows `[ALARM: eval stale Nd]` | No new row appended to `eval_log.jsonl` for >2 days. Usually **downstream** of a t0 alarm rather than an evaluator fault — a day needs ≥24 realised hours in `calibration_history` before it is eligible. | Check `t0_advance_days` in `ml/models/shadow/shadow_state.json` first, and count realised hours per `eval_day`. If a recent day sits just under 24, it self-heals on the next run. See `memory/gotcha-log.md` 2026-08-28. |
| Daily run finishes late, up to the 03:00 UTC deadline, instead of ~16:35 | `wait_for_edh.sh` polled without its **content contract** being satisfied (rewritten 2026-09-01, `7d0066d`): the EDH report must be strictly newer than the last consumed *and* `entsoe` must carry ≥ the median point count of recent publishes. So either EDH published nothing, or it published something short — a pre-auction collection holds same-day prices only (96 vs 192), since the NL day-ahead auction clears ~12:00 CET. **This is the gate working, not a hang.** | Expected fail-open behaviour — it proceeds on stale data rather than freezing the dashboard, and the `[ALARM: t0 stale …]` marker on the same commit records the consequence. `logs/.edh_gate_state` holds the last consumed report timestamp; `logs/daily_update.log` carries the per-poll reason (`entsoe only N points (want >= M)`). A correctly refused short vintage looks identical to a hang from the outside — confirm against the log before intervening. There is **no** `MIN_PUBLISH_HOUR_UTC` floor any more; the old 4h cap and noon-UTC test were removed because GitHub defers EDH's cron unpredictably (observed 00:18–21:14 UTC) and a clock floor shut the gate on good publishes. |
| Build fails with decryption error | Missing or wrong encryption keys | Check Netlify env vars match energyDataHub keys |
| Chart renders but no live data | Energy Zero API down or CORS issue | Check browser console; API tries yesterday if today fails |
| ML inference outputs empty forecast | Model not trained yet | Train with `python -m ml.training.warmup` first (ARF) or wait for next nightly shadow update (LGBM regenerates from parquet) |
| Timezone appears wrong in winter | Hardcoded +2h offset somewhere | Use `Intl.DateTimeFormat` with `timeZone: 'Europe/Amsterdam'` |
