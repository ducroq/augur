# Runbook

## Principles

- **Forecast accuracy > dashboard polish** — the ML pipeline is the core value; the dashboard is the delivery mechanism
- **Continuous learning > batch perfection** — ship a working model, improve daily with online learning
- **Temporal splits only** — never random train/test splits on time series; always split by date
- **energyDataHub is upstream, not ours** — don't modify its data formats; adapt to them

## Local Development

### Prerequisites

- Python 3.12 (deploy box sadalsuud pins 3.12; the venv is locked in `requirements.lock`). Dev box situla currently runs 3.14 — same pinned package set, cp314 wheels resolve, but for exact parity install 3.12.
- [Hugo](https://gohugo.io/) v0.124.0+
- Node.js 16+ (for npm scripts)
- Encryption keys from energyDataHub (ENCRYPTION_KEY_B64, HMAC_KEY_B64)

### Setup

```bash
git clone https://github.com/ducroq/augur.git
cd augur
npm install

# Reproducible Python venv from the pinned lockfile (creates ./.venv).
# Installs the EXACT versions in requirements.lock — NOT the loose ranges
# in requirements.txt (a fresh `pip install -r requirements.txt` is what
# silently pulled bleeding-edge majors during the 2026-07-03 migration and
# broke the ARF pickle). --dev also installs pytest for the test suite.
scripts/bootstrap_venv.sh --dev
source .venv/bin/activate
```

### Running

```bash
# Set keys (bash) — or place them in a .env file (the daily job sources it)
export ENCRYPTION_KEY_B64="your_key"
export HMAC_KEY_B64="your_key"

# Decrypt data
python decrypt_data_cached.py --force

# Run tests
python -m pytest tests/ -q

# Dashboard
hugo server -D
```

## Deployment

### Build Pipeline (Netlify)

The `netlify.toml` build command runs `scripts/netlify_build.sh`:
1. `pip install cryptography` — Python deps
2. `python decrypt_data_cached.py --force` — fetch + decrypt from energyDataHub
3. `hugo --minify` — build static site

Forecasts are generated by the daily systemd timer on sadalsuud (`scripts/daily_update.sh`, gated by `scripts/wait_for_edh.sh`), not during the Netlify build.

### Pre-deploy checklist

- [ ] Encryption keys set in Netlify environment variables
- [ ] energyDataHub publishing to GitHub Pages
- [ ] `--force` flag present in build command (critical — see ADR-003)
- [ ] ML model artifact exists in `ml/models/` if inference step enabled

### Post-deploy verification

- Dashboard loads at deployed URL
- Chart renders with current day's data
- Energy Zero live data refreshes (check browser console)
- Forecast data timestamp is recent (< 24 hours)

### Webhook Flow

1. energyDataHub GitHub Action runs daily at 16:00 UTC
2. Collects, encrypts, publishes to GitHub Pages
3. Triggers Netlify rebuild via `NETLIFY_BUILD_HOOK` secret
4. Netlify decrypts fresh data, runs inference, builds, deploys

## Adding a New Data Feature (ML)

1. Identify the data source in energyDataHub's published JSON files
2. Add extraction logic in `ml/features/online_features.py`
3. Ensure timestamp alignment with existing features (hourly resolution)
4. Handle unit conversion if needed (see `memory/data-formats.md`)
5. Retrain model and evaluate impact on forecast accuracy
6. Update `memory/data-formats.md` if the source has quirks

## Adding a New Data Source to Dashboard

1. Add collector in energyDataHub (separate repo)
2. Update `ml/features/online_features.py` to use the new source as features
3. If client-side visualization needed, update `static/js/modules/data-processor.js`
4. Add to constants in `static/js/modules/constants.js`

## Monitoring the daily job

Three layers, added 2026-08-30/31. Each covers a case the others structurally cannot, so they are deployed together or not at all. Unit files in `scripts/systemd/`; install and rollback recipes in its README.

| Layer | Fires when | Cannot see |
|---|---|---|
| `OnFailure=augur-alert@` (drop-in `augur-daily.service.d/alert.conf`) | the unit **dies** — `set -e` abort, timeout, ExecStartPre failure | anything that exits 0 |
| `augur-heartbeat.timer`, 06:00 UTC | no `Daily update` commit in >30h, timer not enabled+active, or unpushed commits | a bad run that still commits |
| the same heartbeat, reading the commit **subject** | soft failures: `[ALARM: ...]`, `ARF FAIL`, any non-zero step `rc=N`, `rc=skip` | a failure the script never names |

**Why three.** `daily_update.sh` ends with `git diff --cached --quiet && echo "No changes to commit" || {commit; push;}`, so a run producing nothing exits 0 and the unit *succeeds* — `OnFailure=` cannot fire for it. And on 2026-08-30 the production model crashed while the run completed and committed: `shadow rc=1` in the subject, unit green, heartbeat green. Every soft-failure alarm this pipeline raises rides in the commit subject by design, so the third layer is what gives them a reader.

**Channel.** `scripts/notify_email.py`, stdlib only, reading `[email_credentials]` from FluxusSource's gitignored `secrets.ini` on sadalsuud — the same sender `nexusmind-alert@.service` uses. Deliberately no new notification service. Missing creds degrade to a line in `logs/alerts.log` and still exit 0: an alerter that throws inside systemd's failure handling only adds noise. `AUGUR_NOTIFY_SECRETS` overrides the path so a dev-box dry-run cannot send a real email.

**Accepted blind spot.** The heartbeat runs *on* sadalsuud, so it cannot report that sadalsuud is down. Closing that needs an off-host dead-man's switch, i.e. a new service — declined 2026-07-17. The residual case is also the one where daily commits visibly stop.

**Checking it by hand**

```bash
ssh sadalsuud "systemctl show augur-daily.service -p OnFailure --value"   # augur-alert@augur-daily.service.service
ssh sadalsuud "systemctl list-timers augur-heartbeat.timer"
ssh sadalsuud "sudo systemctl start augur-heartbeat.service && tail -3 ~/local_dev/augur/logs/alerts.log"
ssh sadalsuud "sudo systemctl start augur-alert@augur-daily.service"      # end-to-end: sends ONE real email
```

`alert_failure.sh` holds a 3h burst guard, armed only after a **confirmed** send — a skipped or failed email must not silence the next real alert. So a second test fire within 3h logs `email skipped (burst guard)` rather than sending; that is correct, not a fault.

**The job re-execs itself after its own pull** (2026-11-08). bash reads a script by byte offset as it runs, so a pull that changes `daily_update.sh` mid-run used to leave the shell executing misaligned text: on 2026-11-07 it skipped the profile step with no alarm. The script now re-execs once on the pulled file (`AUGUR_DAILY_REEXEC`), and the log shows `Re-executing on the pulled script (<sha>)...` after `Pulling Augur...` every night. **Never change a byte above that block**: an old shell pulling the change must land exactly on it. Pushing a script change is then safe at any time; pulling by hand on sadalsuud while the job sits in `wait_for_edh.sh` is still the clean route.

**Reading an alert.** The email leads with 40 lines of `logs/daily_update.log`, because that is where the error text is: `augur-daily.service` sets `StandardOutput/StandardError=append:`, which **overrides** systemd's journal capture, so `journalctl -u augur-daily.service` holds only lifecycle lines — start, exit code, timeout — and never script output.

## Common Problems

Thinned 2026-11-10. Each row's history and incident dates are in `docs/archive/runbook-common-problems-2026-11-10.md`; grep it by marker. `[NOTE:]` is a result, `[ALARM:]` a fault (see "Monitoring" above).

**EDH gate and data freshness**

| Symptom | Likely cause | Fix |
|---------|-------------|-----|
| `[ALARM: t0 stale <date>]` | EDH published nothing usable, so `wait_for_edh.sh` hit its 03:00 UTC deadline and ran on yesterday's data (fail-open by design). | Nothing in Augur. Check EDH first: `gh issue list --repo ducroq/energydatahub --search "Daily publish is failing" --state open`. No issue plus a stale `t0` is worse: the EDH workflow may not be running at all. Then check publishes directly, from situla (`gh` is not installed on sadalsuud): `gh api "repos/ducroq/energyDataHub/commits?path=data/data_quality_report.json&per_page=5" --jq '.[].commit.committer.date'`. Only `Update energy data` commits carry data; `Record shape observation` commits land on failed runs too. More in `memory/upstream-edh.md`. |
| `[ALARM: EDH publish FAILED upstream — repo#N]` | The gate found an EDH `publish-failure` issue opened after the run started, and gave up early. Fires only on the first night of a streak; later nights show the plain timeout. | Nothing in Augur; the issue number is the diagnosis. |
| `[ALARM: EDH gate timeout — <reason>]`, or the run finishes near 03:00 UTC instead of ~16:35 | The content contract was never met: no report newer than the last consumed, or `entsoe` under the 75th-percentile point count (a pre-auction publish carries 96 of 192). The gate working, not a hang. | `logs/daily_update.log` has the per-poll reason; `logs/.edh_gate_state` the last consumed report. There is no clock floor any more. |
| `[ALARM: EDH entsoe short N/M accepted after 4h]` | The primary feed published short and nothing fuller came within the hold. The vintage is degraded, not lost. | Nothing in Augur (EDH #74). Expect a `t0 held back` or `t0 stale` beside it. `EDH_SHORT_HOLD_HOURS` tunes the wait. |
| `[NOTE: EDH <feed> short at publish N/M]` | A secondary feed (`load_forecast`) came in short. Not a fault. | Nothing. If it costs a feature row, `[ALARM: t0 held back Nh — <feeds> short]` says so on the same subject. |
| `[ALARM: EDH publish Nh stale accepted after Nh]` | Clause (c) (augur#34): the newest report was already there when the run started, and no fresher one came within `EDH_STALE_HOLD_HOURS`. The vintage rests on data up to a day old. | Usually upstream published nothing. If EDH did publish normally, `EDH_STALE_GRACE_HOURS` (default 2h) is too tight. |
| `[ALARM: t0 jumped Nd]` | The parquet advanced more than a day. Either upstream skipped a day, or the gate lagged and a later publish superseded the one it held (ours). | Check ours first: `ssh sadalsuud 'bash -s' < scripts/check_gate_lag.sh`. The skipped day is permanently unevaluable; note the hole wherever a trailing window reads `eval_log.jsonl`. Known holes: 2026-06-08, 2026-06-10, 2026-08-25. |
| Every marker clean, run ends ~16:35, but the forecast is anchored a day back | Gate lag (augur#34): consuming yesterday's unconsumed publish. Every guard reads green. Should be unreachable since clause (c), 2026-09-14. | `scripts/check_gate_lag.sh` prints CURRENT or LAGGED. If LAGGED, clause (c) is off or broken: check `EDH_STALE_GRACE_HOURS`, and that the gate on the box is the committed one (`ExecStartPre` runs before the pull). |
| Dashboard shows old data | EDH's Action didn't run, or the webhook didn't trigger. | Check the Action logs; verify the `NETLIFY_BUILD_HOOK` secret. |
| 72h forecast shows only a short stub; `WARNING ENTSO-E data missing` while EDH is healthy | An EDH schema bump; parsers read the old shape. | Audit `ml/data/consolidate.py`, `data-processor.js`, `tab-charts.js` for top-level `data['<source>']` access; add a `data.get('data', data)` shim. `memory/data-formats.md`. |

**Pipeline steps**

| Symptom | Likely cause | Fix |
|---------|-------------|-----|
| `[ALARM: profile forecast failed rc=N]`, `… Nh of 72]` or `… t0 behind shadow]` | The dashboard's forecaster (ADR-009) failed, ran short, or did not run after a good shadow run. On failure the dashboard keeps last night's file; a run of 24–71 hours writes a new, shorter one (under 24 fails and keeps the old file). `no last_t0` = `update_shadow` never ran. Short = price holes (needs 5 matching days within 56). | Read the log for `Running profile forecast`. Rerun `python -m ml.shadow.update_profile` on sadalsuud and push. Fallback: point `dashboard.js:loadAugurForecast` at `augur_forecast_shadow.json`. |
| `[ALARM: dep probe failed — shadow skipped]` | The sadalsuud venv lost lightgbm/river/pandas. | On sadalsuud, with the job idle (`systemctl is-active augur-daily.service` not `active`; it runs 16:30 UTC until as late as 03:00), move `.venv` aside first (the script reuses an existing venv, and plain `pip install` leaves a corrupt package whose metadata matches its pin), then `scripts/bootstrap_venv.sh` (installs from `requirements.lock`) and rerun the dep probe from `daily_update.sh`. |
| `[ALARM: FM shadow failed exit N]` | Chronos-Bolt shadow failed; the commit normally still lands. `124` = timeout. torch/chronos `ModuleNotFoundError` = venv not from the lockfile. Hugging Face error = pinned revision missing from the cache (`HF_HUB_OFFLINE=1`). A kernel OOM stops the whole job (`OOMPolicy=stop`). | Fix the same day: each missed night is a lost EXP-041 vintage. To stop the shadow, remove the step from `daily_update.sh`. |
| `[ALARM: FM regret failed exit N]` | The FM regret pass failed after a good FM run. Nothing is lost inside the 30-day history. | `python -m ml.shadow.regret --state ml/models/shadow/fm_state.json --regret-log ml/shadow/fm_regret_log.jsonl --model-arm fm` |
| `[ALARM: eval stale Nd]` | No new `eval_log.jsonl` row for >2 days; usually downstream of a `t0` alarm (a day needs ≥24 realised hours). | Check `t0_advance_days` in `shadow_state.json`; a day just under 24 hours self-heals next run. |
| `[ALARM: naive unscored N]` | Eval rows land without `lightgbm_skill_vs_naive`: the floor instrument broke. A real fault. | Check the parquet exists, has `price_eur_mwh` and no duplicate timestamps, and recent `calibration_history` rows carry `t0_utc`. `evaluate_shadow.py:load_price_history` logs which. |
| `[NOTE: naive thin N]`, or the log line `N recent eval row(s) scored on <12 paired hours` | Rows scored on fewer than `MIN_NAIVE_HOURS` (12) paired hours are excluded from the counts. Caused by vintage damage upstream. | Nothing in the evaluator; look at `t0` alarms and EDH outages. |
| `[NOTE: sub-naive L/N]` | LightGBM below the seasonal-naive floor on L of the last N rows carrying a usable naive score (N = 7 once enough exist; after an outage the window spans weeks, not 7 calendar days). A result, not a fault. | Nothing. The augur#29 verdict landed 2026-11-06; this marker is background. |
| ARF outputs an empty forecast | ARF not trained yet. | `python -m ml.training.warmup`. |

**Build and browser**

| Symptom | Likely cause | Fix |
|---------|-------------|-----|
| Build fails with a decryption error | Missing or wrong keys | Netlify env vars must match energyDataHub's keys. |
| Chart renders but no live data | Energy Zero down, or CORS | Browser console; the client falls back to yesterday. |
| Times off by an hour in winter | A hardcoded +2h offset | `Intl.DateTimeFormat` with `timeZone: 'Europe/Amsterdam'` (ADR-008). |
